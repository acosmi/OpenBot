# OpenBot 开源共建与渐进上线策略

> 当前发布裁决（2026-09-05，v4 R204）：**Wrok Bot首版先发布macOS**。
> Windows与Linux按后续版本独立验收；Windows E2继续，但不阻塞macOS首发。
> 本文R189代码/测试快照保留为历史，当前范围见`docs/2026-09-05-WrokBot-macOS首版发布范围与阻断清单.md`。

日期：2026-09-04（America/Los_Angeles）。

本方案基于实际R189主线、正在验收的Screen需求生命周期实现，以及本轮对另一自有项目固定提交的
只读评估。它规划发布顺序，不宣称产品已经上线、已取得开源许可或v4整关完成。
架构与行为继续以v4研究实施方案和GUI第一真源为准；正式变更须写回v4修订记录。

## 1. 已确认的产品方向

用户本轮明确：

1. 尽早交付可用版本，后续持续补齐v4。
2. 第一批面向本人及少量受邀用户的受控试用，不先做公开注册的多租户SaaS。
3. 首版同时具备基础工作台、AI对话与工具闭环、浏览器及电脑操控，不能退化为只有聊天框。
4. 项目计划开源，社区按v4共建，维护者负责PR审查、独立复算和合入。
5. 可评估并复制另一自有项目的必要模块到本项目处理；不得修改源项目代码。
6. 遇到可逆技术选择按第一性原理裁决；未合入的来源变更不冒充稳定基线。

建议把工作分为两条持续交付线：**可用产品线**优先实现上述三类能力的完整用户闭环；
**v4完备线**持续处理平台、协议、治理、供应链、视觉与全部parity/fixture余项。
受控Alpha完成与v4完成分别记账，后者仍必须满足§24 G0–G8和§25十条DoD。

## 2. 为什么可以提早交付，但不能直接宣布当前仓库可发布

当前已有大量Rust生产路径：Agent运行、原生历史/取消、审批/预算、MCP治理与多条GUI journey。
R189机器台账为parity873 done/839 todo、fixtures33 done/21 todo；这些总数不是可用性评分。
当前缺少的正是“别人能拿到、启动并连续完成工作”的产品交付闭环。

本轮直接核到三个约束：

- 根`LICENSE`和Cargo/SPDX仍是专有许可。公开仓库不自动赋予开源使用、修改及分发权；GitHub也明确
  区分公开可见与开源许可。[GitHub许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- Server单用户入口绑定loopback；多用户Server的computer隔离readiness目前仍明确失败。
  不能把这个判断改成true后向公网开放。
- 原生电脑操作依赖本机执行端；一个云端聊天网页不能凭浏览器页面权限自动获得用户电脑的系统控制权。
  本轮评估的自有原生控制底层也有平台与权限限制，尚不能外推为所有平台即插即用。

所以加速方式是缩小**首批平台、部署规模和支持矩阵**，保留三类核心能力；同时做可用安装与真实旅程。
不是把未通过的安全项改绿，也不是先完成所有平台再让第一个人试用。

## 3. 首版产品定义：macOS本机受控 Alpha（R204）

建议首个候选版本命名为`0.1.0-alpha.1`，仅为版本建议，不是现有发布标签。

**首发平台**：macOS；现有本机证据主要为arm64，安装包须明示实际验证的架构和系统版本。
Windows已有可复用底层，保留移植及E2真机验收，安排到后续版本。
一台电脑一个本地用户、一个本地执行端、Rust/PostgreSQL权威数据、
本机Web工作台或同一bundle的轻量本地宿主。先让本人完整使用；受邀用户各自运行独立实例。
不要将单用户服务共享给多个远程用户。Windows不是从零开发任务，但未在OpenBot完成真机验收前
不能列为已支持发行平台；Linux原生桌面后端仍须另行验证。首版明确由macOS先开放，Windows/Linux通过各自验收后再扩展支持。

首版验收必须包含以下三个真实故事：

| 核心闭环 | 用户能实际做什么 | 证明完成的证据 |
|---|---|---|
| 工作台与Agent | 配置自己的API凭据，创建Agent/会话，发送消息，执行一个允许的工具，审批或拒绝，停止任务，重启后找回历史 | 真provider请求、真PG记录、真实GUI操作；取消终态唯一，费用上限生效，错误可恢复 |
| 浏览器操作 | 打开明确指定的网页，读取内容，点击/输入测试表单，看到画面，随时接管或停止 | Rust铸造target/scope与先写审计；真实页面结果、stale ref拒绝、接管期间Agent acting拒绝 |
| 原生电脑操作 | 显式授权本机权限，观察指定应用，批准一次点击/输入，看到实际变化，主动打断并释放按键/鼠标 | 本产品身份的权限证据、动作前后观察与receipt、全局输入互斥、取消/物理接管、secret与像素出网边界 |

“三类都有”不要求首版同时交付所有企业SSO、全部第三方provider live矩阵、所有admin页面与所有OS。
上述能力必须能走通，而未支持的高级入口必须从UI、工具目录和后端执行面共同关闭。
只隐藏按钮不足以控制后端权限；授权仍需在可信服务层验证每个请求。
[OWASP授权检查指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

原生桌面控制超出v4既有Browser/file/shell的部分，应明确登记为用户本轮要求的新增能力；
不能借旧Computer条目的T-ID抹平范围差异。它复用同一Rust审计/权限入口，不自建第二个Agent权限系统。

## 4. 自有模块复用的结论与路线

本轮只读检查确认：浏览器请求适配、进程监管、sandbox/exec有可评估的Rust实现；原生桌面底层也有
独立Rust接口，包含权限、屏幕/区域捕获、应用身份、键鼠/拖拽、AX观察及动作receipt。
初查误用了旧工作分支；用户纠正后，主控已只读核实最近合入的电脑控制PR及最新主分支：
**macOS和Windows均有原生实现**，Windows含输入、屏幕/窗口捕获、UI Automation与接管相关代码。
复用评估改以最新合并基线为准，旧副本作失效调查快照；不再把Windows列为从零开发任务。
没有亲自重跑的签名安装包、真实桌面输入及OpenBot移植验收仍不得记为本轮通过。

已按用户指示将选定Rust底层的固定提交副本放在本项目ignored隔离评估目录，只在副本处理依赖。
源项目未修改；复制本身不表示已进入OpenBot生产依赖图或可公开再许可。
来源内部路径、私有错误文本与原项目内部文档不写进本项目的公开发行材料。

建议按以下方式复用：

| 可复用面 | 处理方式 | 必须重新验收的边界 |
|---|---|---|
| 原生桌面Rust底层 | 从固定提交复制最小闭包，解开源项目workspace继承，建立来源/修改清单；通过独立安全边界接入 | 新产品的权限身份、全局输入互斥、取消、动作receipt、审计先于action、像素出网同意 |
| Rust浏览器适配逻辑 | 选择explicit target、请求约束、timeout/error语义；只把所需逻辑接到OpenBot closed协议 | 不接受自由method/path，不默认active tab，不沿用源项目单用户ACL |
| supervisor/sandbox/exec | 按模块和依赖闭包复制审核，复用进程identity、fidelity及清理经验 | OpenBot的scope/profile/workspace隔离、capability和process-tree取消 |
| Electron宿主 | OpenBot保留既有最小engine与Rust authority；源项目宿主只提供已允许的行为参考 | 不整搬大型TS宿主、账号桥或完整dispatcher，不引入npm或第二条生产browser链 |

复用代码必须先适配OpenBot，再由OpenBot真实验收；源项目的测试通过记录只帮助选择候选。
macOS权限与签名身份不能靠复制原项目的bundle ID、证书、密钥或OAuth client继承。
本机真实键鼠控制是OS用户级共享资源；不能为了品牌替换而把互斥锁拆成互不协调的两套。

源项目后续浏览器优化若与所选模块无关，不阻塞本次评估；后续仍固定新SHA后做差量复核，
不追随未提交工作树或浮动分支。

复制评估的本轮实测：最新合并基线已在隔离目录独立构建。macOS构建暴露的trait导入与借用问题
仅在副本修复；去除没有调用点的捕获库依赖后，现有CoreGraphics捕获路径保留，避免引入未使用的
Swift构建桥。坐标/风险/序列化/图像四组测试实得5+30+14+15项通过；复制副本的Windows x64 locked交叉编译也通过。
这证明所选Rust底层可以从原workspace解开，不证明OpenBot已完成平台权限、真实动作或发行验收。

## 5. 开源策略：先明确可授权代码，再开放共建

用户的开源方向已经明确。下一步是形成可审核的开源范围与发布决议，落实许可证和第三方边界。
建议第一方可授权代码优先评估Apache-2.0；其文本包含明确的专利授权及来源/NOTICE保留要求。
第三方MIT/Apache/字体等仍保留各自许可，不能用一份根许可证覆盖别人的权利。
[Apache-2.0原文](https://www.apache.org/licenses/LICENSE-2.0)

准备顺序：

1. 对拟公开的源码/文档/资产做whole-tree来源审计，分为第一方、已许可第三方、授权复制、
   仅参考/未获公开分发许可四类；每个复制文件绑定固定来源、原/目标hash及修改说明。
2. 对所选自有项目模块明确“允许本地复制”和“允许按目标开源许可证公开分发”两个授权边界。
   不把整个原项目宣布为开源，也不复制其产品身份、服务凭据与内部资料。
3. 固定`grok-bot`参考树保持不变。拟开源的产品导出物按审核后的allowlist生成，
   参考树和未许可材料不混入开源发行包；无法证明分发权的内容不获得新的许可声明。
4. 如采用独立的干净社区仓库，导出必须有原提交/目标文件hash映射，并同步两份第一真源和完整T-ID。
   社区仓只作为干净产品代码入口，不能产生另一套架构真源或静默减少v4分母。
5. 同批更新`LICENSE`、Cargo metadata、SPDX、NOTICE、README和开源范围说明；完成前不宣传“已开源”。
6. 接受社区贡献时建议采用DCO sign-off与贡献来源声明。DCO用于贡献者确认提交来源与授权资格，
   不能替代我们的代码/许可审计。[DCO原文](https://developercertificate.org/)

本方案未擅自修改根LICENSE、源项目许可、远端可见性或公开发布任何复制代码。

## 6. 让社区按v4贡献，而不是让大家各写一套架构

社区入口应有三层：一页产品快速开始、一页贡献指南、按v4/T-ID组织的任务卡。
不要求新贡献者先阅读全部历史Batch才能开始，但每个任务必须附相关章节与不可违反的规则。
GitHub会在Issue/PR入口展示`CONTRIBUTING.md`，可以把这些规则放到实际提交流程中。
[GitHub贡献指南机制](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)

每张可领取任务卡固定包含：

- 用户可见结果、v4章节、相关T-ID；新增行为单独标注。
- 固定基线SHA、允许修改路径、禁止修改路径、依赖任务。
- 一个可以复现的成功场景和必要的失败/越权/取消场景。
- 必跑命令、需要的平台/凭据、应交付的证据格式。
- 领取者、在做/待验收状态；同一范围只有一个执行方。
- 一个可审候选commit或范围紧凑的PR；不将测试通过直接写成中央done。

首批适合开放的任务：官方provider trace、AG-UI/MCP fixture、已有页面的a11y/键盘修复、
独立GUI余页、安装文档/诊断、特定平台测试证据。AuthContext铸造、Vault、policy/audit、
scope/generation、迁移与发行签名等核心边界由主维护者主持方案和审查。

已有外部A/B/C和Personal Skills继续按预留台账处理，不重复领取。任务C本轮已收到候选；
即使定向测试通过，新增第二份package.json、文档计数漂移等问题仍会阻止直接集成，
这是“贡献者实现、维护者独立验收”的实际例子。

## 7. PR审查流程与主干纪律

建议新增`CONTRIBUTING.md`、PR/Issue模板、`SECURITY.md`、`CODEOWNERS`、release支持矩阵；
维护者账号和安全联系地址使用实际配置，不编造账户或邮箱。
CODEOWNERS配合分支保护可要求代码所有者审批，规则本身也应由维护者保护。
[GitHub CODEOWNERS与分支保护](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

一次PR按五步验收：

1. **范围**：基线、T-ID、允许路径与源码来源是否一致，有无无关重构或权限扩张。
2. **代码**：从入口追到实际effect/DB/平台调用，检查空实现、fake成功、错误降级与取消/unknown commit。
3. **独立证据**：维护者在隔离环境对准确候选SHA重跑相关测试，真实平台项由真实平台提供。
4. **台账**：只有本条完整判据满足才改done；不接受仅看总数相同或作者自报绿。
5. **合入与发布**：由授权维护者合入；merge commit保留历史；发布标签、安装包与支持矩阵来自已验提交。

优先缩短PR范围和反馈循环，避免长期堆叠几十批无人审阅的提交。已存在的堆叠历史逐批整理，
不强推改写、不混进“一个小修复”PR。新主干目标是可构建、可启动、无假成功；每次放量来自稳定候选。

Actions继续manual-only，未经用户授权不dispatch；不运行R63禁止的`cargo xtask ci`。
来自外部PR的代码先审再执行，验证环境不带生产secret。开源方向不等于授权恢复自动Actions或自动合并。

## 8. 独立的Alpha发布闸门

应在v4中正式增加受控Alpha里程碑，明确适用对象、平台、数据和支持矩阵；不替代或勾选原G0–G8。
以下是需要实际实现并验收的候选闸门，不是本轮已通过清单：

| 闸门 | 最低通过条件 |
|---|---|
| A0 范围与来源 | 明确支持的三类闭环、平台/部署限制；拟发行文件来源/许可/NOTICE可复算；无未授权材料或secret |
| A1 启动 | 干净目标机器按指南完成预检、配置、启动；readiness真实，无手改数据库或源码才能启动的隐含步骤 |
| A2 Agent | 真provider+真PG+真实GUI完成对话、一个工具、审批/拒绝、取消、超预算与重启恢复 |
| A3 Browser | 指定target的navigate/read/click/type、画面与接管/Stop真实生效；无越scope和绕过审计 |
| A4 原生电脑 | 本产品身份权限、真实动作receipt与结果变化、物理接管/取消、按键释放、全局执行互斥 |
| A5 数据与secret | 权限负向、secret/canary、目标隔离；本机服务不可被未授权远端取得执行权；像素出网需明确同意 |
| A6 运维 | 至少一次本轮新数据backup→restore→checksum演练；升级失败可退回上个已验Rust版本；有日志诊断和停止入口 |
| A7 发行 | 包/二进制摘要与版本相符；自己稳定的产品身份；关闭未支持入口；已知限制与试用范围随包 |

任何已发现P0/P1、跨scope泄漏、audit-before-action违规或不可恢复的数据错误，都不能用Alpha名义豁免。
当前G8要求的三次production-scale旧系统迁移、全平台签名与第二外审仍留在完整发行范围，不能把A6的一次
新数据恢复演练当作其替代证据。按发布物保存可验证的版本与来源，也符合NIST安全开发框架的发布保护思路。
[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)

## 9. 渐进升级路线

| 里程碑 | 用户价值 | 下一阶段前必须补齐 |
|---|---|---|
| Developer Preview | 社区能在公开许可范围内构建、运行和领取任务 | 来源/许可、快速开始、可运行样例、任务/PR规则；不宣称面向普通用户即装即用 |
| 0.1 受控Alpha | 本人及受邀用户在macOS完成三类核心闭环；首发不等待Windows | A0–A7真实通过，稳定的本地身份、安装/诊断、接管与恢复 |
| 0.2 可安装社区Alpha | 扩大受邀自托管，降低安装和配置成本 | 安装/升级/回滚、更多工具与GUI完整度；Windows等后续平台经独立验收后扩张 |
| 0.3 团队Beta | 一支真实团队能够安全协作 | 真多用户身份/隔离、Server runsc平台证据、配额/运维与相关安全审计；不靠单用户服务共享 |
| v4完整发行 | 第一真源全部范围可复算闭合 | G0–G8、十条DoD、全部parity/fixtures及正式golden/平台/供应链/外审/迁移闸门实际通过 |

这些版本是建议的里程碑名称，不是日期承诺，也不意味着后一个阶段的实现现在必须停下。
用户反馈决定同一阶段内的能力优先级；权限、审计、数据与发行来源标准不随反馈降低。

## 10. 接下来先做什么
