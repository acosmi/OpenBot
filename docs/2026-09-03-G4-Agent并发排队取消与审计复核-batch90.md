## 1. 为什么本批必须先于后续 roadmap

Batch89 已把 per-run cost cap 接入 Agent，但一次 run 在进入 provider 前仍会先经过全局 Agent concurrency semaphore。旧实现中，`revoke` 已向这个 activation 发出取消并向 RunRelay 返回 `ChildSignalled`，消费任务却在等待 permit 的分支只删除内存 reservation，未提交 terminal。RunRelay 因此会等待“child 自己收口”，数据库 run 继续保持 running；这破坏了 §7.4 “收到子任务终止事实后才进入 Cancelled”的 durable 闭环，也使后续并发 tool/computer budget 建在错误的取消语义上。

同一轮复核还真实重现 Batch89 的测试集成回归：`AppCommand` 增加两个预算变体后，`transport_parity.rs::http_route_of` 的无 wildcard match 未同步，`cargo test` 在编译期以 `E0004` 拒绝。

## 2. 实现

### 2.1 semaphore 前取消必须 durable terminal

`openbot-agent::runtime::execute_activation` 的两个 permit 前取消入口统一改走 `cancel_before_execution`：

1. 从权威 lease 构造 `AgentState::queued` 与 `DurableTextRun`；
2. 复用唯一 `cancel_and_commit`，经过 reducer 的 `Queued → Cancelling → CommittingResults`；
3. 以 lease 的 expected sequence 提交 `RunTerminal::Cancelled`；
4. terminal 尝试结束后释放 per-run tool sequence，再按 exact lease 清理 reservation。

没有另造数据库写面，没有把 `cleanup` 冒充 terminal，也没有在 RunRelay 侧乐观标记 cancelled。

回归测试以 `max_concurrency=1` 固定占住首个 permit，再激活第二个 run 并撤销。修复前同一测试稳定超时；修复后观察到 `Finish(1, Cancelled)`。这同时覆盖取消在 activation 开始前已经置位与 activation 已阻塞在 semaphore 上的两条入口。

### 2.2 恢复 transport 穷举棘轮

`transport_parity.rs::http_route_of` 显式把 `GetRunCostBudget` / `ReplaceRunCostBudget` 归入“由预算专项 Server/Desktop/Settings 证据承担、不进入 channel transport 矩阵”的分支。仍然没有 wildcard；下一次新增 `AppCommand` 时编译器继续强制作者当场分类。
