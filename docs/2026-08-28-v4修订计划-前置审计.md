## 2. 总体判断

- **方向正确且不是新裁决**：D1（Tauri+Leptos 主 GUI）与 D2（Electron/Chromium 承载不可信内容，且组件与浏览器共用同一 engine 进程类）都是 v3 §0.1 / §3.3 / §11.1 / §13.1 与 R114 已经写死的结论；v4 是重申而非改向。v4 §7.4 "Tauri sandbox renderer 的 todo 目标改为 Electron component engine" 的说法不准确——`T-CMP-0021` 的 `migration_rule` 本来就写着"§3.3 末段写死的必然后果"（同一 Electron engine），从未有过 Tauri renderer 目标。
- **真正的变化只有两处**：D3（`grok-bot` 上升为主要架构/交互参考，优先级高于 OpenBot parity）和 D4（大面积 TS→Rust 语义翻译）。审计的全部主要问题都集中在这两处：它们与第一真源有 4 处未显式 supersede 的冲突、把范围扩大到未裁决的产品面、并把一个 2,111 文件的 census 放在了所有代码之前。
- **v4 处理已完成 693 项的原则是对的**（历史不回写、overlay 另记、`carry` 默认、`remediate` 只针对具体缺陷），但 overlay 的实施方式过重（见 §5）。

## 3. 问题 1 的直接回答：Desktop 沙箱能否用 Rust 原生沙箱替代

**不能替代渲染引擎；但"Rust 原生沙箱"有一个正确且 v4 遗漏的落点——包住 engine 进程。**

组件契约固定为用户 authored HTML/CSS/JS（v3 §3.3，上游 `sandboxed-tools.tsx` 的 `window.__args` 语义），所以必须有一个浏览器引擎执行它。逐一看备选：

| 备选 | 结论 | 理由 |
| --- | --- | --- |
| Servo | 否 | 布局/样式是 Rust，但 JS 引擎是 SpiderMonkey（C++），没有 CDP/screencast/partition 的稳定嵌入面，也没有 Chromium 那样经年对抗敌意内容的多层沙箱；用它反而要自己再造一层沙箱 |
| wry / 系统 WebView 单独进程 | 否 | WebView2 / WKWebView / WebKitGTK 三套引擎、三套隔离语义，帧/输入/egress 无统一控制，Server runsc 内不可用；v3 §2.1 条 2 与 §2.3 条 11 已否决 |
| wasmtime / WASI | 否 | 要求把组件契约改成 WASM，破坏 v3 §3.3 钉死的上游契约 |
| standalone Chromium headless-shell + Rust 直连 CDP（`--remote-debugging-pipe`） | **用户已在 D2 否决** | 它是唯一能让"全量 Rust"回到零第一方 JS 的方案（无 Node、无 shim、无 `ELECTRON_RUN_AS_NODE` fuse 问题）；D2 给的理由"不维护三套 driver"对它不成立（它是一套而不是三套）。这里不重开裁决，只要求 ADR 记录否决理由（例如：Electron 的 `session`/`webContents`/permission handler 与 macOS/Windows 签名发行结构是现成的；CfT headless-shell 的签名/公证与三平台打包需要另立 delta） |
| **Rust 拥有的 OS 沙箱 helper 包住 Electron engine 进程** | **应做，v4 缺** | Electron 主进程天然是 Node（v4 D5 已承认）；renderer 逃逸到主进程 = 拿到 Node = 当前用户全部权限。v3 §10.3 已定义 Desktop 的 sandbox fidelity（Linux ns+seccomp / Windows AppContainer 或 restricted token + Job Object / macOS sandbox profile），v4 D5 也把"平台 sandbox helper"划给 Rust，但只用于 file/shell（G5D）。把同一 helper 用于 launch engine（只放行 pipe handle、profile 目录、egress），才是 G5E"engine compromise 不能扩大 scope"在 Desktop 上的机制；否则 Desktop 的 G5E 只有 renderer 一层 |

## 4. 发现清单

### 4.1 与第一真源冲突、且 v4 没有显式 supersede（合理性 / 一致性）

**F1　`grok-bot` 不是 v3 里的 "Grok Build"，v3 §23.3 的反编译规则与 D3/D4 正面冲突。**
`grok-bot/README.md`、`PROVENANCE.md`、`NOTICE.md` 自述：它是 Anysphere（Cursor）发行的 Grok Bot 0.18.0 macOS 应用的反编译重建（bundle ID `com.anysphere.sand`，"Names and module boundaries inferred from a compiled application"，"No upstream source-code license is asserted or granted"，"complete an independent rights review before public redistribution"）。v3 §1.2 / §23.1 条 3 / CLAUDE.md §9 说的 "xAI Grok Build（Apache-2.0，`19d42e35…`）" 是另一个东西。v3 §23.3 写明"不得把……反编译结果或未授权内部资料当源码"，v3 §11.4 对无授权代码只允许按行为 clean-room 重写；而 v4 D4 的 `T Translate` 定义是"近机械翻译"。用户已裁决权利状态不作为本技术计划的阻断项——本审计不重开该裁决，只要求**一致性**：(a) v4 生成正式真源时必须写一条 R 行显式 supersede §23.3 相关句与 §11.4 clean-room 规则对 `grok-bot` 的适用；(b) CLAUDE.md §9 必须把 "Grok Build" 与 "Grok Bot" 分开写，否则读者会以为 Apache-2.0 覆盖了它；(c) 本仓 public（CLAUDE.md 第 3 行）+ 树内保留原始安装包 LFS 指针 + `T` 类逐函数翻译，三者的组合是否可接受，应作为一条**已知风险**登记在 ADR，而不是从关联方表里消失（v3 §22 有"CrabCode 权利人"一行，v4 §11 没有任何权利人行）。

**F2　"仓库零 `package.json` / Node" 裁决 vs v4 §3.5 的 npm lock。**
v3 §0.1 / §13.1 与 GUI 真源 D2 是 2026-08-22 用户裁决"零 Node"。v4 §3.5 要求 `engine-shim/package.json + package-lock.json`"只钉 Electron 与打包闭包"——这意味着 `npm install electron`，而 Electron 的 npm 包靠 postinstall 从 GitHub 下载二进制，与 v3 §1.2 "缺工具即红不下载"和可复现构建相悖，并引入 npm 供应链面（v3 §16.3 没有 npm audit 闸门）。另外 `grok-bot/` 的引入已经让仓内出现 2 个 `package.json`。建议：Electron 三平台 release zip 以 sha256 钉进 `tools/pins.toml`（当前 pins.toml **没有** Electron 条目，即 43.3.0 目前无处获取）；shim 只保留一个 3 行 app manifest（`main` 字段，零 dependencies，因此无 lock）；对 `grok-bot/` 写一条显式 carve-out（"参考树，CI 永不在其中执行 npm"）并由 `xtask` 反向 grep 锁住。若用户仍要 npm lock，则必须显式撤销 8-22 裁决并补 npm/OSV 闸门。

**F3　D3 把 Grok 置于 OpenBot parity 之上，但产品范围没有裁决。**
v4 §1.1 第 3 层（Grok）高于第 4 层（OpenBot parity），§1.2 又说"GUI interaction/journey：Grok 为主要交互参考"。产品的 parity oracle 是 OpenBot 固定 commit 的 32 个 route / 152 条 UI 条目；Grok 的产品是 Cursor 账号 + 远程 box + `aiserver` Connect RPC（`grok-bot/README.md`），其 GUI 真源是 shipped minified renderer，`frontend/` 只是 partial reconstruction。v4 把 35 个 extension family 与 21 个 GUI family "全部进入 census"、`C` 类只写"候选"、§12.3 把优先级推到 census 之后——等于范围未定。**没有产品范围裁决，census 的分母、v4 总数、P6/P7 的顺序都无法成立**。需要用户裁决：v4 的产品 = OpenBot parity 旅程（保持第 4 层为 GUI 旅程真源）+ 一份点名的 Grok 新能力清单（≤ N 项，各自有 oracle）；Grok 在架构/执行/状态机上是第 3 层参考，在产品旅程上不是。

**F4　修订格式与生效方式不符合仓库自己的规则。**
CLAUDE.md §8："修订方案必须在 §28 风格的修订记录里写 v_n 表述 / 问题 / 修订 / 证据 四列"。v4 是叙事文档，没有 R115；CLAUDE.md §1 与 README 仍把 v3 + GUI 文档列为唯一真源；v4 自称"唯一有效 v4 修订计划"。结果是**两个自称权威的文档并存**，按 CLAUDE.md 入仓首读规则，下一批实施代理会忽略 v4。P0 之前至少要：v3 §28.1 追加 R115（"v4 方向已裁决，正式真源待生成，在此之前 v4 仅约束 P0 工作"）+ CLAUDE.md §1 加一行指针。

**F5　v3 §2.3 十二条"明确不做"没有对 Grok 派生项重申。**
v4 §5.4 的拒绝清单只覆盖 Electron/Node/mock 等实现方式，不含 §2.3 的产品面。Grok 的 `packages/mcp-core`、`host/extensions/mcp`、`host/box/box-mcp.ts` 很可能带 stdio MCP / 常驻连接（§2.3 条 5 否决）；`transcript-mirror`、`agent-store-sync`、`agent-kv`、`state-backstop` 是第二真源形态（§2.3 条 6/9，v4 §6.5 只否了 SQLite/JSON）；`shared/rpc` 是 Connect RPC 全协议（§2.3 条 4 的同类）。应写一句："§2.3 的十二条对 census 里每个 GRB 项同样生效，命中即 `R`，不因来自 Grok 而自动重新立项"。

**F6　v3 §0.4 / §19.1 / §19.2 的 12 人 52 周基线被静默作废。**
v4 §9 "不再给没有实证的日历周数"本身合理，但必须显式 supersede 这三节，并给出一个相对规模登记（v3 剩余 993 项 vs Grok 各类项数），否则"没有日历"会掩盖范围至少翻倍的事实。

### 4.2 遗漏

**O1　Electron 主进程的 OS 沙箱（见 §3 末行）。** v4 §3.4 只约束 renderer；§3.5 还允许 shim "启动 Rust 明确指定的 child/helper"——shim 没有任何需要 spawn 子进程的职责（Chromium 自己起 helper），这条应改为"零 `child_process`"并由 `electron-shim-check` 的 forbidden import 锁死。

**O2　组件 engine 的进程基数、资源与帧路径成本未定义。** §3.3 说"与 Browser Computer 使用不同 Electron process instance；临时 partition/profile"，但没有说 N 个组件同屏时是 N 个 Electron 应用进程（每个自带 browser/GPU/utility 进程，RSS 以百 MB 计）还是一个 role=SandboxedComponent 的 engine 进程内 N 个 ephemeral partition 的 `webContents`（靠 Chromium 的 site isolation 隔离）。§3.3 的"CPU/RSS/wall-clock/frame/DOM 硬预算"没有基数就无从定义；一条 transcript 里 5 个组件 × 各自 CDP screencast × Tauri canvas 的成本也没有估算。v3 §12.6 的 fps/延迟目标只针对 browser computer 的单 viewer。

**O3　Desktop 上 `ExecutionRealm::IsolatedComputer` 是什么没有定义。** Grok 的 "box" 默认是 Cursor 云端沙箱，重建版加了"本地 Docker 容器"替代（`README.md` "Local Docker sandbox"；`electron-main/box/{remote-connector-egress,local-docker-host-connector,egress-tunnel-wiring}.ts`）。v4 §4.8 写"box → runsc/fixed digest"、G5C 写"HostLocal/IsolatedComputer 无隐式 fallback"，但 macOS/Windows Desktop 没有 runsc；若答案是 Docker Desktop，那是 v3 §0.1 允许列表之外的**新外部引擎**，需要独立裁决；若答案是"Desktop Remote 模式由 openbot-server 的 Supervisor 提供"，则应写明 Desktop Local 没有该 realm。

**O4　CSS 预算已耗尽。** 96 KiB 上限只余 456 B（Batch50）。v4 §4.10/§6.8 的 20+ 个 Grok GUI family 会在第一个组件落地时让 `xtask bundle-budget` 判红。GUI 真源 v2 必须先处理（放宽走 delta audit 附实测，或先做 CSS 复用重构），否则 P6 一步都走不了。

**O5　runsc 内 Chromium 沙箱层可行性。** v4 §3.4 禁止 `--no-sandbox` 且要求正向测试证明 renderer 实际 sandboxed；v3 §10.4 要求 Server 固定 runsc。Chromium 的第一层（setuid/user-namespace）沙箱在无 userns 的容器/gVisor 内通常不可用，这正是容器镜像普遍加 `--no-sandbox` 的原因。这不是矛盾但必须 spike 并写成判据："runsc 内要求哪几层（例如 seccomp-bpf layer-2 必须开、namespace layer-1 由 gVisor 替代）"，否则 G5A 与 §10.4 会在实施期互相判红。同一 spike 还要回答 headless/ozone/xvfb 与 GPU-less 的运行方式，v3/v4 均未提。

**O6　shim 的来源谱系未定，v4 全文零次提到 CrabCode。** v3 §11（"Browser Engine 与 OpenBot/CrabCode 复用"）与 §11.4 表把 CrabCode `components/browser-shell` 列为 Electron/Chromium lifecycle/tab/snapshot/input/framing 的复用来源（"权属清理后可用"）。v4 只说"purpose-built shim"，不说它来自 CrabCode（需书面授权编号）、来自 `grok-bot/electron-main`（反编译）还是 clean-room。建议明确 clean-room：shim 应在数百行量级，从 Electron 公开 API 文档写比处理两种权属都便宜；同时 v3 §11.4 表需要一条 R 行写明其处置（保留 / 缩减为 fixture 来源 / 作废）。

**O7　`T Translate` 的 oracle 不存在。** v4 §4.1 的 T 完成条件是"differential fixture + Rust 测试 + production call point"，§4.11 要"先冻结 TS input/output fixture"。但 `grok-bot/source` 与 `frontend` 没有一个测试文件，重建代码本身从未被验证与原应用等价（README："may differ from the original source"），`PROVENANCE.md` 明说"The immutable release is the product specification"。因此差分 fixture 的产生需要：(a) 为无测试的重建 TS 从零搭执行 harness（Node 26 + tsx/esbuild，作为 dev-time oracle 与 cel-js 先例同类，可接受）；(b) 承认 oracle 是"重建代码的行为"而非"原应用的行为"。必须写进 T 的定义，否则 accepted 会冒充等价。

**O8　v3 数值判据没有 carry-forward 登记表。** v4 §8 重写 G0–G8 时把 §12.6（1280×800 / JPEG 70 / 10–15 fps / p95 200 ms / p99 400 ms / 2 秒停播）、§13.2（256/256/50 ms/8 KiB/5 秒）、§17.3 配额、§21.5 SLO、GUI §10.1（110 / 54 张）、§10.5 预算全部省略为"性能""golden"。正式 v4 生成时每条数值要么逐字 carry、要么以 R 行 supersede；建议 P0 先产出这张登记表，防止数值在改写中蒸发。

**O9　Linux Desktop 由 supported 变为"待明确"是回退。** v3 §16.2 把 Linux x64 AppImage/deb 列为 supported desktop；v4 §12.2 说"当前后端真源说支持，GUI golden/Cargo 历史只覆盖 macOS/Windows"。需要裁决而不是搁置：要么 R 行降级 Linux Desktop 为 tier-2，要么补三套证据进 G8。

**O10　零 phone-home 对 Electron 与 Grok telemetry 家族的适用。** v3 §16.4 要求零第一方外发，并把"二进制内出现非配置来源的外部分析域名"设为闸门。Electron/Chromium 二进制本身含大量 Google 域名字符串，闸门范围必须写成"第一方二进制"，否则 engine 一进发行物就红；Grok 的 `telemetry` / `codebase-telemetry` / `analytics-client` / `experiments`（Statsig）/ `source-map` 家族应默认 `R`，v4 §4.6 只对 experiments 与 source-map 表态。

**O11　Windows 上的 boot handshake 需要 spike。** v4 §3.1"通过继承的私有 pipe/handle 完成 boot handshake"在 Windows 上，Rust 父进程向 Electron/Node 传递继承句柄要走 CRT 的 fd 继承块（libuv 读 `lpReserved2`），并不像 UDS 那样直接；更简单的是 stdin 传一次性 boot capability + Named Pipe 名。属实现细节，但 G5A 判据里应有 Windows 一行。

**O12　品牌资产混入。** `eb68406` 携带 `docs/assets/brand-concept/logo-*` 4 个文件，全仓无引用；GUI 真源 §2 说品牌/logo 待 v3 §23.4 商标清查后另立文档。应从 v4 提交中剥离或补文档，否则违反"新增即需修订该表"的纪律。

**O13　Desktop Remote 模式下组件源的获取路径。** Batch50 的 Web 路径靠 Server `/sandbox/runner`；Desktop 连远程 Server 时，Electron 组件 engine 需要经 Axum API 取 published source 再本地注入。v4 §6.9 七步里没有这一步。

### 4.3 过度

**E1　全量 per-symbol census 作为 P0 退出条件。** §7.2 要求 7 份 inventory、每个责任项 15 个字段（class/maturity/target/fixture/production_call_point/state_concurrency…），§9 P0 退出条件是"所有 source responsibility 已有 class/maturity/target"，§13 明确"下一批不应直接写 Browser CDP"。2,111 文件 / 49 万行 TS，AST 只能生成骨架，class/maturity/target/fixture 每条都是人工判断——这是一个以周计的文档工程，而它挡在了**已经卡住 39 条 browser-ops、Desktop renderer、ScreenHub、G5/G7 的 Electron engine 最小闭环**前面，而后者不依赖 census 的任何产出（它本来就是 v3 §11 的既定范围）。建议改成两层：tier-1 文件级（family / maturity / 默认 class，机械生成，一天量级）覆盖全树；tier-2 符号级只在某个能力竖切被 accept 进范围时按需登记。P1 与 tier-1 并行。

**E2　completed-impact overlay 全量分派。** §6.12 要为 693 项各写 disposition + lineage + affected_symbols + affected_test_ids + revalidation。v4 尚未改动任何符号，所以此刻 693 项里除 v4 自己点名的 4 条（T-BROP-0046 remediate；T-CMP-0015/0018 split；T-CMP-0008 措辞）外全部是 `carry`。建议 exception-only：文件只列非 carry 项；每个批次由 `xtask` 按 `git diff` 命中的 `target` 前缀（台账 schema v1 的 `target` 字段是模块路径，可机械匹配）自动追加 `internal_refactor/adapter_rebind` 行并要求重跑。这样 N 才真的是"机械复算"，且不需要 P0 先做一遍。

**E3　§4.2 提前命名约 50 个目标模块**（`openbot-contracts::{desktop,host,execution,…}` 等），与 §7.5 "census 完成前不猜"自相矛盾；应标为候选或删除。

**E4　35 个 extension family 与 21 个 GUI family "全部进入 census"。** `cloud-agents`、`forever-box`、`box-store-sync`、`managed-setup`、`webauthn-proxy`、`host-upgrade`、`trays`、`wallpaper`、`teach-recording`、`cross-user-sharing` 依赖 Cursor 云后端或与 OpenBot 产品无关；应在 tier-1 直接标 `R` 或 out-of-scope，而不是等 census 后再决定。

**E5　台账形态分裂。** `parity/`（schema v1，`parity-check` 只扫这一目录）+ `parity-v4/` + `inventory/grok/` 三处，加 7 种 disposition × 4 种 revalidation。v4 自己承认要扩 `xtask`；建议 disposition 收敛到 4 种（carry / refactor-revalidate / split / superseded；remediate 就是 status=blocked 的 refactor），目录收敛到 `parity/` 下的子目录以复用现有扫描。

### 4.4 关联方

对照 v3 §22，v4 §11 少了：权利人（见 F1）、最终客户/采购（subprocessor 与出网清单：Electron 进发行物后的出网面、Grok 派生 telemetry）、合规/隐私、外部 AG-UI Bot 开发者、MCP vendor、IdP、CopilotKit attribution。多了合理的 Desktop 用户/组件作者/无障碍用户/SRE/QA 行。另外三个 v4 未提但受影响的面：
- **翻译/i18n 工作量**：Grok GUI 文案全部需要 zh-CN，且进入 `xtask i18n-check` 键集合相等闸门；
- **golden 矩阵**：27 页基线之外的每个 Grok 页面按 GUI §10.1 各需 Web 4 张 + Desktop 每平台 2 张；
- **CI/证据来源**：R63 下 Actions manual-only，而 G5A/G8 需要三平台真实进程/签名证据。v4 没有说明 macOS/Linux 证据从哪台机器来。

### 4.5 对已完成项的处理——做对的与两个细节

做对的：不回写历史 status；`carry` 默认；只对有具体缺陷的条目 `remediate`；G1–G6 各节"保留什么、在什么后面接"写得具体，与 CLAUDE.md §1 的未闭合清单一致；`T-BROP-0046`、`T-CMP-*` 的 ID 引用与台账逐条对得上；§6.3 指出的"read checksum 已闭合 / 深校验未闭合"文案冲突是真实存在的。

两个细节：
1. `T-BROP-0046` 的 remediate 是**断言正确性**问题，不是现实风险（epoch 要递增 2^64 次才饱和）。修法（`checked_add` → poisoned 状态 → 清 lease、拒输入直到 ComputerGeneration 推进）便宜，应做，但不宜作为 §5.3 的头条"协议缺口"来定性 Batch51。
