## 4. 第二阶段：基于验收后的状态拆分 v4

首发平台已经用户固定为macOS；具体范围见 `docs/2026-09-05-WrokBot-macOS首版发布范围与阻断清单.md`。
继续落实宿主/启动方式、单用户部署、实际启用provider/tool、开放页面及三条用户故事。
以 v4 §24.2 和既有 A0–A7 为准逐项复核；支持矩阵尚未确定时不能把某项直接判为非阻断。
审计的结果应是一份有证据、有依赖的上线清单，而不是以文件数、PR 数或全量 done 百分比评估能否上线。

每个未闭合 T-ID / fixture，以及没有既有 T-ID 的新增原生电脑能力，逐项记录以下信息：

| 字段 | 要求 |
|---|---|
| 原身份 | 第一真源章节、原 T-ID / fixture；新增要求单列，不借旧条目抹平范围 |
| 当前证据 | 实际候选/集成 SHA、复算命令、passed/failed/ignored、真实平台或测试替身范围 |
| Alpha 关联 | 影响哪个已开放用户故事、支持平台和 A0–A7 判据；注明生产调用是否可达 |
| 发布分类 | 上线前必须完成 / 首版后近期补齐 / 后续 v4 完备；尚不能判断则暂列待证据 |
| 分类理由 | 不完成会导致什么真实用户失败或安全/数据问题；后置时如何从 UI、目录及后端关闭该能力 |
| 下一动作 | 最小必要实现或证据、依赖/外部输入、负责人及可以独立验收的完成条件 |

分类使用下列规则，不能仅按模块名称一刀切：

- **上线前必须完成**：A0–A7 的实际缺口；三条故事不可用；首批平台无法干净启动/安装、授权或停止；
  已开放路径的 P0/P1、跨 scope 泄漏、audit-before-action 违规、secret 泄漏、失控输入、不可恢复数据错误；
  拟交付文件的来源/许可及产品身份问题。已有严重缺陷不能改个标签就后置。
- **首版后近期补齐**：不阻断上述故事、且对首批用户有明确增益的可独立功能与体验改进。
  不为了追齐整个管理界面或组件目录而推迟三条核心故事的闭环；已交付且验收合格的低风险功能可按依赖集成。
- **后续 v4 完备**：未列为首批支持的平台、未启用的企业/协议/管理能力、全平台和完整视觉矩阵、完整生产规模迁移等。
  只在首版范围确实不依赖、后端实际禁用或隔离、且未违反 A0–A7 时后置；仍保留原 todo 和最终证据要求。
- **外部阻塞**是单独的原因字段，不自动决定优先级。若它阻断首版已启用路径，就仍是上线阻断；
  若可排除对应平台/能力而保住三个核心故事，则记录支持范围调整后继续独立工作。

边界示例均待验收后逐条落表，不代表本轮已批准延期或已通过：

- 首期实际启用的 provider 必须有真请求、工具/取消、预算和 secret 证据；未启用 provider 的完整 recorded/live 矩阵仍留在 v4。
- 公开多租户、企业 SSO、Server KMS 等是否阻断取决于真实发布形态和可达依赖，不能把模块名列入延期表就绕开共享风险。
- 完整 golden/全路由矩阵与首版实际开放页面分开记账；三条故事的真实 GUI、键盘/焦点、必要可访问语义和中英文质量须实际验收。
  不得用结构检查冒充正式 golden 或 G6。
- 完整旧系统 production-scale 迁移不等于首版新数据恢复；A6 的本轮 backup → restore → checksum 与升级失败恢复仍要实跑。
- 开源共建可以持续准备，但本轮指令不自动授权更换许可证、公开私有材料、发布安装包、推送其它分支或合并 PR。
